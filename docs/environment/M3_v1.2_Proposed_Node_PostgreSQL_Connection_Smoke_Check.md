# Proposed M3 v1.2 Addition: Node-to-PostgreSQL Driver Connection Smoke Check

**Document ID:** CDCMS-M3-ADD-001  
**Proposal revision:** 0.3  
**Proposed version target:** M3 Environment Readiness Checklist v1.2  
**Status:** Draft proposal; not part of M3 v1.1 and not yet adopted  
**Prepared:** 2026-11-06  
**Purpose:** Supplement the existing environment checks with an OS-labelled, reproducible test that a Node.js process can load the candidate `pg` package and connect to a dedicated local PostgreSQL database.

> **Status and execution warning**  
> This is a proposed addendum, not a replacement checklist and not evidence that the test has been run. M3 v1.1 has not been edited. No machine test is reported by this document. The M3 v1.1 contents are described according to the review supplied for this project: separate Express and `argon2` checks, plus PostgreSQL client-version, service, and server-readiness checks. Those checks do not establish Node-driver connectivity.

## 1. Revision 0.3 changes

This revision addresses the review findings:

1. Uses the `pg` default-import pattern instead of a named import, then explicitly checks that `Client` is available before attempting a connection.
2. Labels commands separately for Ubuntu/Linux Bash and Windows PowerShell.
3. Provides steps to create a dedicated local probe role and database; the probe must not use the PostgreSQL superuser account.
4. Uses a temporary `PGPASSFILE` stored in the scratch directory, with restrictive permissions/ACLs, instead of putting the password in a command or relying on a password-bearing shell-history entry.
5. Suppresses raw database/client error messages and prints only a sanitized diagnostic code and the failed stage.
6. Explains that import/package failure, connection failure, and database authentication failure are different results and must not be conflated.
7. Removes the final `exit` commands from the Ubuntu and PowerShell run blocks. Each block now prints the captured Node probe exit code and returns control to the open terminal without closing it.

## 2. Why this check is proposed

A PostgreSQL service can be installed and running, and `psql` can be available, while the backend's Node process still has a package import, driver, connection, authentication, or query problem. This check tests the actual Node-to-PostgreSQL driver path rather than inferring it from `psql` or service readiness.

The `pg` package is a **candidate used to test the current backend direction**, not a final dependency decision. The team must record the exact Node.js, `pg`, npm, and PostgreSQL versions tested. As of the preparation date, node-postgres documents ESM support from the 8.15.x line and shows both its current ESM import guidance and the earlier default-import pattern. This proposal uses the default-import form to avoid depending on CommonJS named-export detection in older package versions; the selected version must still pass the pilot import check. See the sources in Section 12.

## 3. What the probe proves—and what it does not

A successful run proves, for the tested machine and versions, that:

1. Node can resolve and load the selected `pg` package using the script's default-import form.
2. The Node process can connect to the configured local PostgreSQL instance using a dedicated login role.
3. The driver can execute a basic SQL query.
4. The driver can create a temporary table and complete an insert, update, and read-back inside a transaction, then roll the transaction back.

It does **not** prove:

- that the final Express application is correctly wired to PostgreSQL;
- that the eventual application database role, schema, migrations, or application permissions are correct;
- that production connection pooling, deployment networking, TLS, backups, or recovery are correct;
- that the project has selected `pg` as its permanent driver;
- that MAC-007 has passed.

MAC-007 still requires a later application-level test showing that the actual backend performs the intended persistent PostgreSQL update and can read the resulting state. This temporary-table probe is environment-readiness evidence only.

## 4. Preconditions and safety rules

- Run M3 v1.1 first on the machine. Confirm its applicable Node/npm and PostgreSQL client/service/server-readiness prerequisites before proceeding.
- Run on each workstation expected to develop or run the backend. The first pilot should be the Ubuntu workstation; only extend to the Windows workstations after the Ubuntu procedure is understood.
- Use a local development PostgreSQL instance. Do not point the probe at a live school, shared production, or otherwise sensitive database.
- Create a dedicated, low-privilege local role and database for this probe. Do not use the PostgreSQL `postgres` superuser for the Node script.
- Use a fresh, clearly identified scratch directory outside the project repository. Do not place the script, `.pgpass`, `node_modules`, or temporary npm files under `android/`, `backend/`, `web/`, or `docs/`.
- Install the exact `pg` version selected for the backend if the team has selected one. Otherwise, install a candidate, record the exact resolved version, and do not treat the result as final dependency approval.
- Use a temporary password file as described below. Do not write a password into SQL text, shell commands, PowerShell commands, source files, screenshots, issue trackers, or public test output.
- Do not modify `pg_hba.conf`, loosen authentication, grant superuser rights, or broaden database permissions just to make the probe pass. Record a blocker and investigate the actual local configuration instead.
- Do not share raw stack traces or raw database/client error messages. They can include usernames, database names, local paths, or host details.

## 5. Create a scratch project and install the candidate driver

The following commands create a temporary npm project outside the repository. If the team has selected a specific `pg` version, replace the unpinned install command with `npm install --save-exact pg@X.Y.Z` using that exact version.

### Ubuntu / Linux Bash

```bash
mkdir -p "$HOME/cdcms-m3-pg-probe"
cd "$HOME/cdcms-m3-pg-probe"
npm init -y
npm install --save-exact pg
npm ls pg --depth=0
```

### Windows / PowerShell

```powershell
New-Item -ItemType Directory -Force -Path "$HOME\cdcms-m3-pg-probe" | Out-Null
Set-Location "$HOME\cdcms-m3-pg-probe"
npm init -y
npm install --save-exact pg
npm ls pg --depth=0
```

Record the exact `pg` version shown by `npm ls`. If npm cannot reach the registry or installation fails, mark the driver check **BLOCKED** at the package-install stage. Do not label that a PostgreSQL connection failure.

Save the script in Section 8 as `m3-pg-smoke.mjs` in this scratch directory.

## 6. Create a dedicated local PostgreSQL role and database

Use the same names on each workstation unless a name already exists. If either `cdcms_m3_probe` role or database already exists, do not overwrite, reset, or drop it automatically. Stop and select a unique suffix for this workstation, then substitute that suffix consistently in the SQL and connection settings below.

The example uses:

- Database role: `cdcms_m3_probe`
- Database: `cdcms_m3_probe`
- Host: `127.0.0.1`
- Port: `5432`

### Ubuntu / Linux Bash

1. Open a terminal.
2. Connect to the local PostgreSQL administrator account through the operating-system `postgres` account. On the common Ubuntu package setup, this local-socket administrator connection uses peer authentication; it is separate from the probe's TCP/password connection.

```bash
sudo -u postgres psql -d postgres
```

3. At the `psql` prompt, first check that the names are unused:

```sql
SELECT rolname FROM pg_roles WHERE rolname = 'cdcms_m3_probe';
SELECT datname FROM pg_database WHERE datname = 'cdcms_m3_probe';
```

If either query returns a row, stop and choose a new unique suffix. Otherwise, create the role and database:

```sql
CREATE ROLE cdcms_m3_probe LOGIN;
\password cdcms_m3_probe
CREATE DATABASE cdcms_m3_probe OWNER cdcms_m3_probe;
\q
```

The `\password` prompt asks for the role password without placing the clear-text password in the SQL command or psql command history. Use a unique password for this disposable local test account.

4. Verify that the role can log in over TCP, not just through the local peer-authenticated administrator socket:

```bash
psql -h 127.0.0.1 -p 5432 -U cdcms_m3_probe -d cdcms_m3_probe -W
```

Enter the password at the prompt. At `psql`, run:

```sql
SELECT current_user, current_database();
\q
```

If this connection fails, record the failure before running the Node probe. Do not change authentication configuration just to bypass the result.

### Windows / PowerShell

1. Open PowerShell. The PostgreSQL command-line tools must be available on `PATH`. If `psql` is not recognized, open **SQL Shell (psql)** from the PostgreSQL Start Menu group and use the same connection values below; alternatively, use the installed PostgreSQL `bin` directory's `psql.exe` path.
2. Connect to the local PostgreSQL administrator account. The example assumes the installer-created administrator role is named `postgres`; use the actual local administrator role if the installation used another name.

```powershell
psql -h 127.0.0.1 -p 5432 -U postgres -d postgres -W
```

3. At the `psql` prompt, check that the role and database names are unused:

```sql
SELECT rolname FROM pg_roles WHERE rolname = 'cdcms_m3_probe';
SELECT datname FROM pg_database WHERE datname = 'cdcms_m3_probe';
```

If either query returns a row, stop and choose a new unique suffix. Otherwise, create the role and database:

```sql
CREATE ROLE cdcms_m3_probe LOGIN;
\password cdcms_m3_probe
CREATE DATABASE cdcms_m3_probe OWNER cdcms_m3_probe;
\q
```

Enter the new role password only at the `\password` prompt.

4. Verify the role can log in over TCP:

```powershell
psql -h 127.0.0.1 -p 5432 -U cdcms_m3_probe -d cdcms_m3_probe -W
```

Enter the password at the prompt, then run:

```sql
SELECT current_user, current_database();
\q
```

If the administrator login, role creation, database creation, or TCP login is unavailable, record **BLOCKED** and the step that could not be completed. Do not edit `pg_hba.conf` as an ad hoc workaround.

## 7. Set local connection details without shell-history passwords

The `pg` client reads standard PostgreSQL connection environment variables such as `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, and `PGPASSFILE`. Use a temporary password file in the scratch directory so the password is not part of the shell command, PowerShell command, or repository. PostgreSQL documents the password-file format and permission requirements in its official documentation.

**Password-file rule:** use a random password containing letters and digits only for this disposable probe account. This keeps the password-file line simple because colon and backslash characters need escaping in the file format. Do not reuse a personal, school, or production password.

### Ubuntu / Linux Bash

Run this from the scratch directory containing `m3-pg-smoke.mjs`. These commands are designed to be pasted into an already-open interactive terminal. They capture and print the Node probe's exit code but do not call `exit`, so the terminal remains open. If you save a block as a wrapper script instead, run that script from an already-open terminal; the wrapper should likewise omit an `exit` command.

```bash
umask 077
read -rsp "Password for cdcms_m3_probe: " M3_PROBE_PASSWORD
printf '\n'
printf '127.0.0.1:5432:cdcms_m3_probe:cdcms_m3_probe:%s\n' "$M3_PROBE_PASSWORD" > .pgpass
unset M3_PROBE_PASSWORD
chmod 600 .pgpass

export PGHOST=127.0.0.1
export PGPORT=5432
export PGDATABASE=cdcms_m3_probe
export PGUSER=cdcms_m3_probe
export PGPASSFILE="$PWD/.pgpass"

node ./m3-pg-smoke.mjs
PROBE_EXIT_CODE=$?

unset PGHOST PGPORT PGDATABASE PGUSER PGPASSFILE
rm -f .pgpass
if [ "$PROBE_EXIT_CODE" -eq 0 ]; then
  printf 'Probe process exit code: 0 (PASS)\n'
else
  printf 'Probe process exit code: %s (FAIL; inspect the result table above)\n' "$PROBE_EXIT_CODE"
fi
# Deliberately do not call `exit`: keep the interactive terminal open.
```

The `read -s` prompt does not echo the password. `umask 077` and `chmod 600` restrict access to the temporary password file. The script removes the file after the run.

### Windows / PowerShell

Run this from the scratch directory containing `m3-pg-smoke.mjs`:

```powershell
$passFile = Join-Path (Get-Location) '.pgpass'
$securePassword = Read-Host 'Password for cdcms_m3_probe' -AsSecureString
$bstr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($securePassword)
$probeExitCode = 1

try {
    $plainPassword = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($bstr)
    $line = "127.0.0.1:5432:cdcms_m3_probe:cdcms_m3_probe:$plainPassword"
    [System.IO.File]::WriteAllText(
        $passFile,
        $line + [Environment]::NewLine,
        [System.Text.UTF8Encoding]::new($false)
    )
    Remove-Variable plainPassword

    $currentSid = [Security.Principal.WindowsIdentity]::GetCurrent().User.Value
    & icacls.exe $passFile /inheritance:r /grant:r "*${currentSid}:F" | Out-Null
    if ($LASTEXITCODE -ne 0) {
        throw 'Could not restrict access to the temporary password file.'
    }

    $env:PGHOST = '127.0.0.1'
    $env:PGPORT = '5432'
    $env:PGDATABASE = 'cdcms_m3_probe'
    $env:PGUSER = 'cdcms_m3_probe'
    $env:PGPASSFILE = $passFile

    node .\m3-pg-smoke.mjs
    $probeExitCode = $LASTEXITCODE
}
finally {
    $env:PGHOST = $null
    $env:PGPORT = $null
    $env:PGDATABASE = $null
    $env:PGUSER = $null
    $env:PGPASSFILE = $null
    if (Test-Path $passFile) {
        Remove-Item $passFile -Force
    }
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($bstr)
    $securePassword.Dispose()
}

if ($probeExitCode -eq 0) {
    Write-Output 'Probe process exit code: 0 (PASS)'
} else {
    Write-Output "Probe process exit code: $probeExitCode (FAIL; inspect the result table above)"
}
# Deliberately do not call `exit`: keep the interactive PowerShell session open.
```

If the ACL command fails, the script stops before running the database probe. Do not continue with a password file whose access restrictions could not be applied. The file is removed in the `finally` block.

## 8. Probe script

Save as `m3-pg-smoke.mjs` in the scratch directory:

```js
import pg from 'pg';

const { Client } = pg;

if (typeof Client !== 'function') {
  console.error('FAIL: the pg default import did not expose Client.');
  console.error('Treat this as a package/import failure, not a database connection failure.');
  process.exit(1);
}

function safeDiagnosticCode(error) {
  const code = typeof error?.code === 'string' ? error.code : '';
  return /^[A-Za-z0-9_-]{1,32}$/.test(code) ? code : 'not-provided';
}

const client = new Client({
  connectionTimeoutMillis: 5000,
  query_timeout: 5000,
  statement_timeout: 5000,
  application_name: 'cdcms-m3-pg-smoke',
});

let connected = false;
let connectionPassed = false;
let basicQueryPassed = false;
let temporaryWritePassed = false;
let transactionOpen = false;
let serverVersion = 'not obtained';
let stage = 'connect';

try {
  await client.connect();
  connected = true;
  connectionPassed = true;

  stage = 'basic query';
  const versionResult = await client.query(
    "SELECT current_setting('server_version') AS server_version"
  );
  serverVersion = versionResult.rows[0]?.server_version ?? 'unknown';
  const pingResult = await client.query('SELECT 1 AS connection_check');
  if (pingResult.rows[0]?.connection_check !== 1) {
    throw new Error('Basic query returned an unexpected value.');
  }
  basicQueryPassed = true;

  stage = 'temporary write/read probe';
  await client.query('BEGIN');
  transactionOpen = true;

  await client.query(`
    CREATE TEMP TABLE m3_pg_smoke (
      id INTEGER PRIMARY KEY,
      status TEXT NOT NULL
    )
  `);

  const insertResult = await client.query(
    'INSERT INTO m3_pg_smoke (id, status) VALUES ($1, $2) RETURNING status',
    [1, 'inserted']
  );
  if (insertResult.rowCount !== 1 || insertResult.rows[0]?.status !== 'inserted') {
    throw new Error('Temporary-table insert did not return the expected row.');
  }

  const updateResult = await client.query(
    'UPDATE m3_pg_smoke SET status = $2 WHERE id = $1 RETURNING status',
    [1, 'updated']
  );
  if (updateResult.rowCount !== 1 || updateResult.rows[0]?.status !== 'updated') {
    throw new Error('Temporary-table update did not return the expected row.');
  }

  const readResult = await client.query(
    'SELECT status FROM m3_pg_smoke WHERE id = $1',
    [1]
  );
  if (readResult.rows[0]?.status !== 'updated') {
    throw new Error('Temporary-table read-back did not return the updated value.');
  }

  await client.query('ROLLBACK');
  transactionOpen = false;
  temporaryWritePassed = true;
} catch (error) {
  console.error(`Failed stage: ${stage}`);
  console.error(`Sanitized diagnostic code: ${safeDiagnosticCode(error)}`);
  console.error('Raw error text suppressed to avoid disclosing usernames, database names, hosts, or paths.');
  process.exitCode = 1;
} finally {
  if (connected) {
    if (transactionOpen) {
      try {
        await client.query('ROLLBACK');
      } catch {
        // Preserve the original failure; raw rollback details are intentionally suppressed.
      }
    }
    try {
      await client.end();
    } catch (closeError) {
      console.error(`Connection-close warning; sanitized diagnostic code: ${safeDiagnosticCode(closeError)}`);
      console.error('Raw close-error text suppressed.');
      process.exitCode = 1;
    }
  }
}

console.log(`Node.js: ${process.version}`);
console.log(`PostgreSQL server version: ${serverVersion}`);
console.log(`Node-to-PostgreSQL connection: ${connectionPassed ? 'PASS' : 'FAIL'}`);
console.log(`Basic SQL query: ${basicQueryPassed ? 'PASS' : 'FAIL/NOT RUN'}`);
console.log(`Temporary INSERT/UPDATE/SELECT and ROLLBACK: ${temporaryWritePassed ? 'PASS' : 'FAIL/NOT RUN'}`);

if (!connectionPassed || !basicQueryPassed || !temporaryWritePassed) {
  process.exitCode = 1;
}
```

From the scratch directory, run `node --check m3-pg-smoke.mjs` first to check JavaScript syntax. This does not resolve/import `pg` and does not test the database connection. Then run the script using the OS-appropriate `node` command already shown in Section 7. Do not run it from the repository.

### Classify failures correctly

- If Node reports an inability to resolve/import `pg` before the script emits its own stage/output, record a **package/import failure**. It is not a PostgreSQL server, authentication, or database failure. Redact local paths before sharing any import stack trace.
- If the script prints `Failed stage: connect`, record a connection-stage failure. Use only the printed diagnostic code; do not copy raw error text into shared notes.
- If the connection passes but a later query fails, record the actual failing stage. Do not report the entire probe as PASS.
- Do not print or share `error.message`, `String(error)`, stack traces, connection strings, environment dumps, or password-file contents.

The script intentionally prints only the stage and a constrained diagnostic code for caught database/client errors. Diagnostic codes such as `ECONNREFUSED`, `28P01`, `3D000`, or `42501` can help classify a failure without disclosing the full connection error. The code is not guaranteed to be present for every failure.

## 9. Result recording

For every tested workstation, record:

| Field | Record |
|---|---|
| Machine label | Sanitized label such as `Ubuntu-Developer`, `Windows-Developer-A`, or `Windows-Developer-B` |
| Operating system | Version/build at a level safe to share; exclude private machine identifiers |
| Node.js | Exact `node --version` result |
| npm | Exact `npm --version` result |
| PostgreSQL client | Exact `psql --version` result from M3 v1.1 |
| PostgreSQL server | Version reported by this script |
| `pg` package | Exact resolved version from `npm ls pg --depth=0` |
| Package import | PASS / FAIL / BLOCKED |
| TCP role/database login via `psql` | PASS / FAIL / BLOCKED |
| Node connection | PASS / FAIL / BLOCKED |
| Basic query | PASS / FAIL / BLOCKED |
| Temporary write/read/rollback | PASS / FAIL / BLOCKED |
| Notes | Sanitized stage, diagnostic code, cause, and corrective action; no credentials or private machine details |

Use **BLOCKED** when the check cannot be run because a prerequisite, local administrator account, role/database setup, package installation, or test account is unavailable. Use **FAIL** when the step ran and exposed an import, connection, authentication, query, or permission problem. Do not convert either status to PASS without a successful rerun and evidence.

A connection can PASS while the temporary write probe fails because the role lacks temporary-table privileges. Record the sub-results separately and investigate whether that limitation reflects the intended local development configuration. Do not broaden database privileges merely to make the smoke check pass.

## 10. Cleanup

After recording the results, remove the dedicated probe database and role if they were created solely for this check and are no longer needed. Connect as a local PostgreSQL administrator to the `postgres` maintenance database, then run the following commands only when you have confirmed that these exact names belong to this probe and no one else is using them:

```sql
DROP DATABASE cdcms_m3_probe;
DROP ROLE cdcms_m3_probe;
```

Do not add `CASCADE`. If PostgreSQL reports active connections or dependencies, stop and resolve the situation deliberately rather than forcing deletion. If a unique suffix was used, substitute that exact suffix.

## 11. How to use the result for TD-011 and MAC-007

- Successful runs on the required developer environments provide direct evidence that the tested Node runtime, tested `pg` package, and tested PostgreSQL server can connect and execute the limited probe together.
- A successful result does not automatically select Node 26.13.0, approve `pg` as the final backend dependency, or settle TD-011 in full. The owner/team must assess the other M3 evidence and all relevant stack constraints.
- This proposal does not select the team's PostgreSQL role naming, privilege model, migration approach, or final application connection configuration.
- A successful temporary write test does not satisfy MAC-007. During backend implementation, add an application-level test that creates or updates a representative fictional project record through the backend's actual database access path, reads it back, and verifies the persisted result.
- If the team chooses another PostgreSQL driver, adapt and rerun an equivalent test using the selected driver before treating that runtime/driver/database combination as checked.
- If the owner/team does not adopt or run this probe, TD-011 must explicitly state that Node-driver connectivity remains unverified; do not infer a PASS from `psql` readiness.
